Tutorial: docking with flexible receptor side chains

This tutorial re-docks a known ligand into its native receptor while treating some receptor side chains as flexible. It uses the same system as the re-docking tutorial: CDK2 (PDB 4EK3) and one of its ligands (PDB 4EK4).

You will learn to:

  • compute affinity maps for a pocket with flexible receptor side chains
  • run ADFR to re-dock the ligand into the receptor with flexible side chains

Prerequisites: ADFRsuite 1.0 installed with ADFRsuite-1.0/bin on your PATH, and the tutorial data downloaded and unzipped (see Tutorials).

1. Generate the target file

Flexible residues are given on the command line with the -f/--flexRes option and a selection string, for example "A:ILE10,VAL32;B:SER48".

A target file for the 4EK3 pocket that binds the crystallographic ligand, with ILE10 and LYS33 flexible, could be computed with:

agfr -l data/4EK4_lig.pdbqt -r data/4EK3_rec.pdbqt -f A:ILE10,LYS33

However, agfr fails here: the docking box, built with the default 4 Å padding around the ligand, is too small to cover the flexible side chains.

To fix this we increase the padding to 8 Å. To save time in this tutorial we also compute maps only for the atom types present in the ligand (-m ligand).

agfr -l data/4EK4_lig.pdbqt -r data/4EK3_rec.pdbqt -f A:ILE10,LYS33 -P 8.0 -m ligand -o 4EK3_rec_FR_10_33
Option Meaning
-r the receptor file
-l the ligand file
-f the receptor side chains to make flexible. Their atoms do not contribute to the grids. Separate residues from different chains with a semicolon, for example "A:PHE80;B:LYS89".
-P padding added around the ligand’s bounding box (here 8 Å)
-m ligand compute maps only for the atom types present in the ligand
-o name of the target file to create

3. Dock the ligand

adfr -l data/4EK4_random.pdbqt -t 4EK3_rec_FR_10_33.trg --jobName flexRes --nbRuns 8 --maxEvals 20000 -O --seed 1

ADFR docks the ligand into the receptor while treating the 2 side chains A:ILE10 and A:LYS33 as flexible. adfr detects the available cores and uses all of them by default. Here it runs 8 independent searches (--nbRuns 8), each with up to 20,000 evaluations of the scoring function (--maxEvals 20000). By default adfr runs 50 searches of 2.5 million evaluations each. Harder docking problems need more searches to raise the chance of finding the best pose (the global minimum of the scoring function). The low values here give a quick run that is enough to show how docking works.

The run writes 3 files:

File Content
4EK4_random_flexRes_summary.dlg the docking log, with most of the messages printed to the terminal and extra clustering information
4EK4_random_flexRes_out.pdbqt multi-model pose file with the solutions
4EK4_random_flexRes.dro the docking result object: input, output and metadata of this run
TipNotes
  • Output files are named after the ligand, followed by the job name (--jobName, if given).
  • The search is stochastic: docking the same ligand into the same target twice can give different results with different random seeds. Setting the seed (--seed) makes a run reproducible for a given version of the code. See the re-docking tutorial for details.

Here the 8 searches found 4 distinct solutions, sorted by predicted affinity, best first. The top solution was found by 4 of the 8 searches (clust. size), and its best pose came from search 3 (best run). The second solution was found once and is 2.8 Å RMSD from the top solution (clust. rmsd). With a reference ligand (--reference), the ref. rmsd column would give the RMSD of each pose to the reference instead of −1.

NoteReview note
  • The CCSB “you will learn” list says 3 flexible side chains; the commands make 2 flexible (A:ILE10, A:LYS33). Written as 2 here.
  • The CCSB text said the target file was for “PDB id 1EK3”; the files are 4EK3. Corrected.
  • The CCSB text says the command also uses “the AutoSite 1.0 algorithm -as”, but no such option appears in the command. Dropped.
  • The CCSB output file names used flexRec; the job name and the console output use flexRes. Corrected to flexRes.
  • The CCSB text said “up to 20’000 evaluations (--maxEvals 2000)”; the command uses 20000.
