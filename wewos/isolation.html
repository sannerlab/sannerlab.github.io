Networks from other people

A network file is a program. When you open one that someone else made, WEWoS can run it in a sandbox, where its code cannot reach your files or the internet.

Why a network needs care

  • Opening a network runs the code of the nodes whose code was edited, including its top-level statements.
  • Running it runs every node. Some standard nodes evaluate their widget values as Python: eval, Call Method, If, While and others.
  • Vision's *_net.py files are imported without being run, but the edited code they contain runs as soon as the imported network opens.

In Vision, all of this ran with your rights. In WEWoS, a network from someone else can run in its own process, confined by the operating system.

Three levels

Levelits code can readits code can writeinternet
Sandboxedits own folder, the folders you add, and the Python environment WEWoS runs inits own folderoff, unless you allow it
Read-onlyevery file you can readits own folderoff, unless you allow it
Unrestrictedevery file you can readevery file you can write yes

Unrestricted is how WEWoS runs the networks you make yourself.

Choosing a level

  • File > Open network and File > Import a Vision network (and dropping a file on the page) ask how the network should run. Sandboxed is chosen the first time; after that, the dialog offers the level you chose last. It is remembered in settings.json in the folder of your networks.
  • File > Open an example asks the same question, offering the level you chose last for a file; the choice made for an example is not remembered.
  • New networks, which start empty, run unrestricted.
  • The badge next to the run status shows how the current network runs: 🛡 sandboxed or 🛡 read-only, with · internet when it may use the internet, or 🔓 unrestricted. The open networks menu marks the isolated ones with 🛡.
  • The canvas of an isolated network is tinted and framed in the badge's color, pale green when it is sandboxed and pale amber when it is read-only, with its level in the top right corner, so that you see at a glance which networks are confined.
  • File > Isolation of this network… (or a click on the badge) changes the level. The network is saved, closed and opened again from its autosave at the new level, so the results of its last run are not kept. Once you have read a network's code and trust it, you can make it unrestricted this way.

Internet access

A sandboxed or read-only network has no internet access unless you tick Allow internet access. Fetch PDB works without it: WEWoS checks the four-character PDB id and downloads the entry from the RCSB for the network. Allow the internet only for a network that needs other downloads. A read-only network with internet access could send any file you can read to another computer; the dialog says so.

Files

  • A sandboxed network sees its own folder only. Bring data files in with the Upload button of a file widget, or list folders under Also let it read these folders when you choose the level: it can read them, not change them.
  • The file browser of a sandboxed network shows what the network can see, so your home folder looks almost empty there.
  • Downloads of the network's files and of its folder never follow a symbolic link: a network cannot make WEWoS hand you, or read, a file outside its folder.

Stopping

Stop (■) waits for the running node to finish, as in Vision. If an isolated network has not stopped five seconds later, WEWoS offers Force stop, which ends the network's process and starts it again from its last autosave. The network is kept; the results of that run are lost. File > Force stop does the same at any time.

How it works

  • An isolated network runs in its own Python process, confined by the operating system:
    • Linux: bubblewrap. The process has its own namespaces (processes, users, network), sees the files of its level only, and has no capabilities.
    • macOS: sandbox-exec, which comes with macOS, with a profile WEWoS writes for the level: what the process may read and write, and whether it may use the network.
    • Windows: an AppContainer, Windows' own app sandbox, one per network, in a Job object that ends it, and whatever it started, when the server ends or on Force stop. The network's folder and the folders you grant are opened to that AppContainer only; it reaches the internet only when you allow it.
  • It ends when the WEWoS server ends. Its memory is limited to three quarters of the machine's on Linux and Windows (macOS does not apply that limit), and a file it writes to 4 GB on Linux and macOS.
  • The server passes the page's requests on to it, and the page keeps working as usual: editing, widgets, runs, the 3D viewers and picking.
  • The page accepts scripts only from the WEWoS server and talks only to it (a Content-Security-Policy). Text and pictures from a network are shown as text and pictures, never as code.

Limits

  • Isolation needs Linux with bubblewrap (apt install bubblewrap on Debian and Ubuntu), macOS, or Windows 8 or later. When the server starts, it checks that WEWoS runs under the sandbox; if not, File > Isolation of this network is greyed out, networks run unrestricted, and the reason is shown. python -m wewos.isolation says where it fails.
  • On Windows, once: wewos sandbox-setup. An AppContainer can read only the folders that allow it, and Python environments usually do not: this command lets Windows app sandboxes read (not change) the Python environment and the WEWoS folder, with icacls. It takes a minute for a large environment.
  • No read-only level on Windows. A process there can be kept from writing your files while it reads them, but keeping it off the internet then needs administrator rights; the dialog shows the level greyed out. Use Sandboxed, and grant the folders the network must read.
  • On macOS, sandbox-exec is marked as deprecated by Apple, although macOS itself and programs such as web browsers still rely on the sandbox it starts.
  • A sandbox lowers the risk; it is not a guarantee. A flaw in the Linux kernel could let code out, and the worker has no system-call filter.
  • A network can still use all the processor, fill the disk of its folder, or show you results that are wrong on purpose.
  • Node libraries of your own that you load after an isolated network was opened are not available to it until it is opened again.
  • To run a WEWoS server for other people, start it with wewos serve --isolation sandboxed (or readonly): every network, including new ones and examples, then runs at least at that level, and the server refuses to load Python modules or files into itself.
